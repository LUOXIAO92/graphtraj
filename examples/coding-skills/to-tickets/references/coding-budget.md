# Task execution budget

Read the current Ticket's budget and accepted scope before dispatch. Estimate
actual implementation and validation needs, reuse known findings and evidence,
and count only the selected work and Sessions. Professional phases can describe
an estimate; they do not define a separate task lifecycle or mandatory roles.
Use the installed task definition schema and preserve its existing values on
continuation. Difficulty does not itself choose a model or increase the budget.

Present the expected time and configured executor before launch. Keep the
original Ticket-shared accounting, thresholds and stop policy. Record a changed
scope or estimate through the existing task revision workflow with its cause;
that revision alone grants neither extra time nor permission to resume.

The Runner sends budget notices to the task's actual parent. Keep that parent's
live notice channel connected to the awaiting execution; a saved log or pending
queue entry does not establish delivery. The parent coordinates its children.
Runner independently enforces a selected stop without waiting for notice handling.

An estimate or allowance notice is not an enforced stop. On a delivered notice,
assess its supplied facts and the remaining work once. Use event-driven follow-up
and the project's shared polling limit; do not start another monitoring loop.

On an actual stop preserve files, commits, task/Session bindings and Traces and
collect only the permitted retained wrap-up. Use [recovery decisions](../../../../manuals/task-delivery/references/recovery.md)
for the existing authorization and continuation path. Stopping does not authorize
new implementation, Review, replacement, a reset or an extra window.
