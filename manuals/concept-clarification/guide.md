# Concept Clarification

Identify the term, distinction or relationship that prevents a clear decision.
Read the existing vocabulary and relevant decisions first. Apply settled
meanings instead of asking the user to decide them again.

Use concrete scenarios to distinguish concepts: what counts, what does not,
and what changes when one interpretation replaces another? Compare how the
terms are actually used with their stated definitions. Resolve synonyms and
overloaded names only when the distinction matters to the work.

Separate observations, assumptions, proposed definitions and accepted choices.
A contradiction needs its source and a scenario showing the conflict. Resolve
ordinary wording from available evidence; ask only when different meanings
would change the user's intended outcome or a substantive decision.

Record the agreed definition, important relationships and a useful example in
the project's existing glossary or the artifact that needed clarification.
Preserve explicit disagreements and unresolved boundaries. Create a separate
record only when it helps retain a real decision; do not require a new glossary,
ADR directory or document structure for every clarification.

The result is language the next task can use consistently, not a software
architecture or implementation prescription. Follow the project's document
ownership and write permissions; return proposed wording when direct editing
is outside the assignment.
