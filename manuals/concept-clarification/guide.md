# Concept Clarification

Identify the term, distinction or relationship that prevents a clear decision.
Read the existing vocabulary and relevant decisions first. Apply settled
meanings instead of asking the user to decide them again.

A term the user explicitly asks to define, or one that decides whether
something may start, counts, is included or excluded, or ends, needs the
user's confirmation. Neighbouring glossary entries, other documents and
customary or outside usage only supply a proposed meaning for it. Resolve
other ordinary wording from available evidence; ask only when different
meanings would change the user's intended outcome or a substantive decision.

Use concrete scenarios to distinguish concepts: what counts, what does not,
and what changes when one interpretation replaces another? Ask with one
concrete case per interpretation, such as "if X happens, does it count as Y?",
and check the points that change a count or decision: who determines it, when
it applies, what confirms it and what is excluded at the start. Compare how
the terms are actually used with their stated definitions. Resolve synonyms
and overloaded names only when the distinction matters to the work.

Separate observations, assumptions, proposed definitions and accepted choices.
A contradiction needs its source and a scenario showing the conflict. When an
accepted record and the artifact disagree in a way that changes the outcome,
quote both, show the consequence and let the user choose; change neither side
before the answer.

Ask before editing: do not write an unconfirmed meaning into the files; put
the proposed wording in the question. Meanings already settled in the records
may still be applied. While a meaning the outcome depends on is unconfirmed,
the clarification is not finished: end with the question, not a completion
claim.

Record only meanings the user confirmed or the records state, with important
relationships and a useful example, in the project's existing glossary or the
artifact that needed clarification. Mark other details as proposed or leave
them out. When a meaning replaces an earlier one, keep a note of the replaced
meaning. Preserve explicit disagreements and unresolved boundaries. Create a
separate record only when it helps retain a real decision; do not require a
new glossary, ADR directory or document structure for every clarification.

The result is language the next task can use consistently, not a software
architecture or implementation prescription. Follow the project's document
ownership and write permissions; return proposed wording when direct editing
is outside the assignment.
