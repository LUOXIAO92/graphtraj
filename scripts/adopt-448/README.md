## 418's hook-module change and production's copy (team judgement)

Production's `hooks/host_context.mjs` is written by `configuration --write`
(`graftling/claude/plugin.py`). It comes from `src/graftling/claude/host_context.mjs`
with `const PLUGIN = null;` unchanged. Only the marketplace package replaces that
line, with `"graftling"`.

From d11f3226 (production now) to 2be27dd6, only 418's two commits touch this file:
09871709 and 3a95423a, 85+/10−. So the bytes of production's copy change, and V
records the diff in `raw/V-plugin.diff`. Every new branch, though, is guarded by
`PLUGIN`, so in production it is dead code:

- 3a95423a's `projectMaterial()` (the check of the inherited `GRAFTLING_CLAUDE_HOST_CONFIG`) runs only `if PLUGIN`.
- `pluginPython`, `pythonReport` and the `--project-from` context command are also plugin-only.
- `state.inert` and `state.foreignConfig` stay false.

The local path keeps reading `GRAFTLING_CLAUDE_HOST_PYTHON` and
`GRAFTLING_CLAUDE_HOST_CONFIG` and runs `graftling.claude.host context --config`.
`PREFIX` stays `mcp__agents__`.

Judgement: in production the change reaches the copy as bytes only. Behaviour does
not change. The one visible effect is a possible plugin/hooks trust dialog on
resume. V checks `^const PLUGIN = null;` in the candidate and stops if it is
missing.

418's reminder (an inherited config from another project makes the old hook give
up association) concerns the plugin form. Step 00 still reports any inherited
name with its path, and the script unsets them for its own child commands.
